## Code of Conduct

Be respectful and constructive. Assume good intent, keep discussions focused on the work, and avoid personal attacks in issues, pull requests, or discussions. Maintainers may edit, close, or lock threads that don't follow this spirit. See [CODE OF CONDUCT](./CODE_OF_CONDUCT.md) for details.

## Getting Started

### Prerequisites

- [Node.js](https://nodejs.org) (LTS version recommended)
- npm (bundled with Node.js)
- Git

### Setup

1. **Fork** the repository on GitHub.
2. **Clone** your fork locally:
   ```bash
   git clone https://github.com/<your-username>/ChromeOS-Recovery-Image-Downloader.git
   cd ChromeOS-Recovery-Image-Downloader
   ```
3. **Install dependencies**:
   ```bash
   npm install
   ```
4. **Start the dev server**:
   ```bash
   npm run dev
   ```
   Vite will print a local URL (typically `http://localhost:5173`) — open it in your browser to see live-reloading changes.
5. **Build for production** (to sanity-check your changes build cleanly):
   ```bash
   npm run build
   ```

## Project Structure

This is a Vite + Vue 3 project. At a high level:

```
ChromeOS-Recovery-Image-Downloader/
├── .github/          # Workflows (incl. the catalog-generation job) and Dependabot config
├── public/catalog/   # Recovery image catalog data, kept up to date by a scheduled workflow
├── scripts/          # Helper scripts (e.g. the catalog generator run by the workflow)
├── src/               # Application source code
├── index.html         # Entry HTML
├── vite.config.js     # Vite configuration
└── package.json
```

If you're adding a new device/board or changing how recovery images are listed, it most likely belongs alongside the existing components and logic in `src/` — look for the existing catalog-consuming code to follow established patterns. Changes to how the catalog itself is generated belong in `scripts/` and `.github/workflows/`.

## Development Workflow

1. Create a new branch off `master` for your change:
   ```bash
   git checkout -b feature/short-description
   ```
   Use a prefix that describes the change, e.g. `feature/...`, `fix/...`, `docs/...`, `refactor/...`.
2. Make your changes, testing them locally with `npm run dev`.
3. Run the linter before committing (see below).
4. Keep pull requests focused — one logical change per PR is much easier to review than a large mixed-purpose one.

## Coding Guidelines

- **Language:** Write new code in the style already used in the project (plain JavaScript with Vue 3 Single File Components); keep components small and focused rather than mixing unrelated concerns into one file.
- **Linting:** Run the linter and fix any issues before opening a PR:
  ```bash
  npm run lint
  ```
- **Consistency:** Match the formatting, naming, and file organization conventions already used in the codebase rather than introducing a new style in an unrelated PR.
- **Catalog data:** Don't hand-edit files under `public/catalog/` — that data is generated by the scheduled GitHub Actions workflow. If the catalog looks wrong or stale, fix the generation logic in `scripts/`/`.github/workflows/` instead.
- **No unrelated changes:** Avoid bundling formatting-only or unrelated refactors into a functional PR — it makes review harder and obscures the actual change.

## Commit Messages

Write clear, descriptive commit messages in the imperative mood, e.g.:

```
Add search filter for board names
Fix incorrect file size formatting on download cards
Update README with new deployment instructions
```

Reference related issues where relevant, e.g. `Fixes #12`.

## Submitting a Pull Request

1. Push your branch to your fork:
   ```bash
   git push origin feature/short-description
   ```
2. Open a pull request against the `master` branch of `MYTAditya/ChromeOS-Recovery-Image-Downloader`.
3. In your PR description, include:
   - What the change does and why.
   - Screenshots or a short clip/GIF for any visual/UI changes.
   - Any related issue numbers.
4. Be responsive to review feedback — small follow-up commits are fine; you don't need to force-push/squash until asked.
5. A maintainer will review, request changes if needed, and merge once it looks good.

## Reporting Bugs

Please [open an issue](https://github.com/MYTAditya/ChromeOS-Recovery-Image-Downloader/issues) and include:

- A clear, descriptive title.
- Steps to reproduce the issue.
- What you expected to happen vs. what actually happened.
- Screenshots, if the bug is visual.
- Your browser/OS, if relevant.

Search existing issues first to avoid duplicates.

## Suggesting Features

Feature ideas are welcome via [issues](https://github.com/MYTAditya/ChromeOS-Recovery-Image-Downloader/issues) or [pull requests](https://github.com/MYTAditya/ChromeOS-Recovery-Image-Downloader/pulls) — describe the use case and, if you can, how it might fit into the existing recovery-image browsing flow. Since this project mirrors the interface of Google's own Chromebook Recovery Utility, keep proposals aligned with that simple, familiar look rather than introducing unrelated design directions.

## Security Issues

Please **do not** report security vulnerabilities through public GitHub issues. See [SECURITY.md](./SECURITY.md) for how to report them responsibly.
